# D10 numeric API audit (active)

D10 is not passed. All assigned API catalog entries remain pending while their complete argument domains, generic witnesses and delivery gates remain open.

The concrete integral factory increment uses mathematical integer bounds. CreateSaturating clamps to the target interval; CreateTruncating keeps the target-width residue; CreateChecked requires a source proof that every executed input fits. BigInteger has no finite integral target bound. Native comparisons cover every integral source/target pair, Char inputs, signed/unsigned boundaries and large BigInteger magnitudes. The reference implementation is the pinned [.NET 10 Int32 source](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/System.Private.CoreLib/src/System/Int32.cs) and [.NET 10 BigInteger source](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/System.Runtime.Numerics/src/System/Numerics/BigInteger.cs).

The Decimal increment is under validation. Decimal-to-integral saturating and truncating factories clamp the truncated value. Both Decimal.ConvertToInteger and Decimal.ConvertToIntegerNative use saturating conversion. Integral-to-Decimal saturating/truncating factories clamp to the exact 96-bit coefficient range; checked factories require the corresponding source bounds. Decimal-to-Decimal factories retain coefficient, scale, sign and SDK value. This follows the pinned [.NET 10 Decimal source](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/System.Private.CoreLib/src/System/Decimal.cs); it does not replace intrinsic Decimal arithmetic or failed proofs with saturation.

The checked API name denotes a failure-prone library function. A proved-safe source call has no checked syntax or checked semantic conversion node. Explicit checked syntax and checked semantic arithmetic/conversions continue to reject under the master policy. Unknown conversion safety fails the whole frontend conversion.

The independent integer-factories distribution combines an original Elm IR model with the frozen original D5 helper distribution. Its source/output provenance is recorded in fixtures/D10/expected/provenance.json. No frontend output creates or refreshes expected JSON, and the production compatibility sources remain unchanged.

Floating/Complex factory mappings and standard floating integer APIs have a source increment under validation. Native primitive conversions and general checked floating bounds remain gated; unresolved generic numeric witnesses and full cumulative D10 gates remain pending. Complex-to-BigInteger uses a real-component cast even for saturation/truncation, so NaN still fails; direct floating-to-BigInteger saturation/truncation maps NaN to zero. See the pinned [Complex source](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/System.Runtime.Numerics/src/System/Numerics/Complex.cs) and [BigInteger source](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/System.Runtime.Numerics/src/System/Numerics/BigInteger.cs). The pinned [.NET 10 Double source](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/System.Private.CoreLib/src/System/Double.cs) distinguishes native floating conversions from its saturating integer API; their equality is not assumed.

Native comparison found an additional .NET10 JIT distinction: Single.ConvertToInteger<byte>(-1.99f) returns255 through primitive conversion, unlike the managed CreateSaturating fallback. Standard Single/Double primitive integer APIs therefore use the fixed unchecked cast mapping under validation. Half and nonprimitive targets retain saturating conversion. Native primitive APIs still require their separate platform mapping.

The new bounds increment tracks NaN separately from finite interval endpoints. The false side of an ordered comparison does not exclude NaN. Proved finite/truncated target bounds permit CreateChecked and platform-independent safe native conversions. Half.ConvertToIntegerNative uses the pinned managed saturating fallback; Single/Double native overflow/NaN behavior remains rejected without a deterministic proof. The [official native API contract](https://learn.microsoft.com/en-us/dotnet/api/system.double.converttointegernative?view=net-10.0) explicitly gives platform-specific overflow behavior.

Generic factory bodies retain ordinary input/output type variables and explicit required conversion callbacks. Requirement identity includes exact source/target types and conversion mode. Only pinned INumberBase/IFloatingPoint conversion contracts and their exact concrete implementations are mapped. Concrete callback construction invokes the same full-domain safety checks as direct lowering; incomplete/unproved conversions fail at their source call, including unreachable calls/references. Full source static-interface constraints and guarded partial generic numeric specialization remain later D10 work.
